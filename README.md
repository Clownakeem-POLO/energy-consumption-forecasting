# Appliance energy use forecasting

I predict how much energy a home's appliances draw (in Wh) from indoor sensors,
outdoor weather, and the time of day. The point of the project is to treat this
as a time series, not a bag of sensor readings, and to be honest about what that
buys me.

There is a live demo built with Streamlit (`app.py`) where you can set the
conditions and read a prediction.

## The problem

Buildings and homes are a big slice of energy demand, and appliance load is the
part that swings the most through the day. If you can forecast it even a little,
you can shift loads, size storage, or flag unusual use. This is a small, honest
version of that: one house, 10 minute readings, a model you can actually run.

## The data

UCI Appliances Energy Prediction. It is a real CSV of 19,735 readings taken
every 10 minutes over about 4.5 months from a single house in Belgium. Each row
has the appliance energy use (the target, in Wh), a lights channel, indoor
temperature and humidity from 9 rooms, and outdoor weather (temperature,
pressure, humidity, wind, visibility, dew point).

Source: https://archive.ics.uci.edu/dataset/374/appliances+energy+prediction

I drop the two columns named `rv1` and `rv2`. They are random noise the dataset
authors added on purpose as a control, so they carry no signal.

## The approach

The differentiator here is the feature engineering, which lives in
`src/features.py` so the notebook, the app, and the tests all share it.

- **Time features** from the timestamp: hour of day, day of week, a weekend
  flag, and month. These let the model learn the daily and weekly rhythm of when
  people are home and using things.
- **Lag features** of the target: the reading 10 minutes ago, the reading one
  hour ago, and a rolling mean of the last hour. Energy use is sticky, so recent
  history is the strongest predictor I have.
- The **sensor and weather columns** that come with the data.

I compare a plain linear regression against histogram gradient boosting, and I
split **by time, not at random**. The first 80 percent of the timeline is for
training and the last 20 percent is held out in order. A random split would let
the model train on readings that come after the ones it is tested on, which is
cheating for a time series and would never happen in production. The scores
below are lower because of this, and that is the point. They are honest.

## Results

Measured on the held out last 20 percent of the timeline.

| Model              |   RMSE |    MAE |    R2 |
|--------------------|-------:|-------:|------:|
| Linear regression  |  61.67 |  28.11 | 0.540 |
| Gradient boosting  |  64.06 |  37.94 | 0.504 |

The honest surprise: the linear baseline wins. Once the lag features are in,
most of the signal is close to linear, so the extra flexibility of gradient
boosting mostly gives it room to overfit. I tried deeper and faster boosting
settings and added early stopping, and it still landed behind. So the model the
app ships is the linear one. I would rather report that than quietly swap in a
fancier model that does worse.

For scale, the target has a mean around 98 Wh and a long right tail up to 1080
Wh, so an MAE near 28 Wh is a usable everyday estimate that still misses the big
spikes.

## Limitations

I want to be straight about what this is and is not.

- **One house.** The model learns this one household's habits. Point it at a
  different home and it would need retraining. There is no claim of generality.
- **It undershoots spikes.** The residuals widen at high predicted values. If
  the goal were catching demand surges, I would switch to a quantile loss or a
  model aimed at the peaks, and I would measure it differently.
- **Lag features need recent history.** The strongest inputs are the last few
  readings of the target itself. In a real deployment you need a live feed of
  recent energy use, not just weather. The app lets you type those in by hand so
  you can see their effect.
- **Short window.** About 4.5 months means the model never sees a full year, so
  seasonal effects beyond the `month` feature are not really learned.
- **Not causal.** This is a correlational forecast. It tells you what usually
  happens under these conditions, not what would happen if you changed one.

## What I would do next

- Try a quantile or peak focused objective to handle the spikes.
- Add longer lags and a rolling standard deviation, carefully, to avoid leakage.
- Validate with a rolling or expanding window instead of a single split.

## How to run it

From the project folder on Windows (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

On macOS or Linux, swap the activate line for `source .venv/bin/activate`.

Then:

```bash
# 1. Build and execute the notebook. This trains the models, saves the figures
#    to figures/, and writes the model to model/energy_model.joblib.
python build_notebook.py

# 2. Run the tests.
pytest

# 3. Launch the demo.
streamlit run app.py
```

The dataset is already in `data/`. If you need to fetch it again, it is the
`energydata_complete.csv` file from the UCI link above.

## Deploying the demo

The app is ready for Streamlit Community Cloud. Point it at this repo with
`app.py` as the entry point and `requirements.txt` for dependencies. The trained
model is committed under `model/`, so the app has what it needs without
retraining.
